# Encrypting S3 objects and EBS volumes with AWS KMS

- **Date:** 2026-11-17
- **Topic:** Cloud Security
- **Source:** AWS Academy Learner Lab (Cloud Security), Lab 5.1 "Encrypting Data at Rest by Using AWS KMS"
- **Time spent:** 75 min

## What I learned

- KMS uses envelope encryption. The KMS key never leaves KMS. Instead, it creates a data key that encrypts the actual data. An encrypted copy of the data key is stored alongside the data.
- A KMS key has two kinds of permissions: key administrators manage it, and key users can encrypt and decrypt with it.
- Even after I made an SSE-KMS object public, it still couldn't be read anonymously. Reading it needs a signed request from someone who is allowed to use the key.
- You can't encrypt an existing EBS volume in place. You stop the instance, snapshot the volume, create an encrypted volume from the snapshot, then swap it in as the root volume.
- Disabling the key immediately blocks access to everything it protects. The instance couldn't boot and the S3 object couldn't open until I turned the key back on.
- CloudTrail logs every key use, such as GenerateDataKey, Decrypt, CreateGrant and DisableKey, along with who did it.

## Commands, queries or snippets

```bash
CloudTrail: filter event source to kms.amazonaws.com to see key usage
Encrypt existing root volume: stop -> snapshot -> new encrypted volume (same AZ) -> detach old -> attach new as root device -> start
```

## Why it matters for security

Encryption with KMS adds a second layer on top of access policies. A misconfigured public bucket doesn't leak readable data if the attacker can't use the key. The flip side is that an attacker who can disable or schedule deletion of a key can make your data unusable, ransomware-style. Key permissions and DisableKey or ScheduleKeyDeletion events need close watching.

## Questions / next step

- Learn key policies vs. grants, and how key rotation works.
- Set up an alert on DisableKey and ScheduleKeyDeletion events.
